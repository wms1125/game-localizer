# GLM 视觉判官六场景评测

日期：2026-08-13

## 结论

视觉辅助复核模型选择 `glm-4.6v`，但它必须与本地 OCR/确定性硬门组合使用，且不能独立授予发布 `pass`。

- `glm-4.6v-flash` 的有效响应覆盖不足，并且对已经获得响应的两个漏汉化页面均给出 `pass`。
- `glm-4.1v-thinking-flash` 完成全部六场景，但漏检了全部三个已知缺陷场景。
- 因未能创建 Gemini API Key，本轮没有获得 Gemini 的真实结果，不能声称智谱优于或弱于 Gemini。
- 付费 `glm-4.6v-flashx` 虽然请求和 JSON 均稳定，但仍漏检全部三个已知缺陷场景，不符合默认判官资格。
- 付费 `glm-4.6v` 在历史六场景上实现请求成功率 100%、JSON 合规率 100%、漏检率 0%、误报率 0%，因此成为当前质量优先的辅助模型。
- 当前 v14 正常候选通过 140/140 项 OCR/布局/字体硬门，六场景 GLM 复核全部通过；该历史报告的最终决定为 `pass`，新策略不再允许 GLM 单独授权自动通过。

## 方法

使用 Ren'Py 官方 `The Question` 的历史 `r6` 六场景成对截图。第一张为英文参考，第二张为简体中文候选。采用历史截图是因为当前 `v14` 六场景已经全部修复，只含阴性样本，无法计算漏检率。

六个场景以场景级计分：

| 场景 | 真值 | 依据 |
|---|---|---|
| `main-menu` | 有缺陷 | 游戏标题仍为 `The Question` |
| `dialogue` | 无缺陷 | 对话与快捷菜单已汉化 |
| `branch` | 无缺陷 | 分支选项与对话已汉化 |
| `settings` | 无缺陷 | 外语内容均为语言名称，按规则允许 |
| `save` | 有缺陷 | `Page 1`、`empty slot` 和英文日期残留 |
| `load` | 有缺陷 | `Page 1`、`empty slot` 和英文日期残留 |

同组比较中的模型使用完全相同的中文提示词、图片顺序、问题分类与五字段 JSON 契约。每个场景独立请求，温度为 0。付费模型测试只压缩发送给远端的截图副本为 JPEG 90，原始 PNG、哈希和本地硬门证据不变；这是为了避免 Windows Python 对约 5.8 MB 双 PNG 请求发生 TLS EOF。

## 风险与后续

所有受测 GLM 都不能被信任自行填写 `model` 字段。生产适配器使用客户端配置的模型标识覆盖模型自报值。

对 `glm-4.1v-thinking-flash` 另做了一次不计入盲测指标的 OCR 诊断：要求它逐字转录 `save` 候选截图。模型准确返回了 `Page 1`、五处 `empty slot` 和英文日期。这说明 100% 漏检并非看不见文字，而是单阶段视觉判定提示词的指令执行失败。后续更值得验证的是“视觉 OCR 提取 + 本地确定性残留规则”的两阶段方案，而不是继续把同一个免费模型直接用作最终裁决者。

本轮六场景结果只能作为接入门槛，不能证明泛化质量。Gemini 对照已按当前产品决策取消。仓库现已新增 36 场景受控合成集：4 个正常对照，以及漏翻、截断、溢出、重叠、缺字、乱码、错误换行、样式/可读性八类缺陷各 4 个变体；固定 960x540 画布、生成器版本、字体记录和逐场景机器真值。如果后续成本压力要求切换 `flashx`，必须先证明其漏检率改善，而不能仅因价格较低就降级。

原始六场景运行报告保存在本机 `.tmp/visual-judge-benchmark-*.json`，其中不包含 API Key；历史 r6 截图和真值不纳入版本库。新增受控数据集位于 `benchmarks/visual_judge_controlled/`，由 `tools/generate_visual_judge_dataset.py` 可重复生成并由 `tests/test_visual_judge_dataset.py` 锁定。

## 受控集 v2 门槛复测

首次执行 36 场景诊断时发现两个评测前提错误：中文候选的固定页眉和存档标签仍保留英文，并且请求向模型发送了包含缺陷类别的 `sample_id`。因此该轮虽然得到 36/36 请求成功、36/36 JSON 合规、总体漏检 8/32 的结果，也不能作为正式盲测结论。报告仅作为诊断记录保存在本机，SHA-256 为 `35a634fda832826c3c2a47d06e32ae0fa99d50e07247a4370830180f542db422`。

生成器已升级为 `hanengine.visual-judge-controlled/v2`：中文候选的标题、章节、按钮和存档标签全部汉化；提示词不再包含场景 ID，并明确逐区域检查文字重叠、异常单字换行、字号和低对比度。为避免在无效方案上继续产生付费调用，先对“上一轮漏掉的 8 个缺陷 + 4 个正常对照”执行门槛复测，而不是直接重跑全部 36 场景。

| 指标 | `glm-4.6v` v2 门槛子集 |
|---|---:|
| 请求成功率 | 12/12，100% |
| JSON 合规率 | 12/12，100% |
| 正常对照误报率 | 0/4，0% |
| 已知缺陷漏检率 | 7/8，87.5% |
| 错误换行召回 | 1/1，100% |
| 重叠召回 | 0/3，0% |
| 样式/可读性召回 | 0/4，0% |
| 中位响应时间 | 13.16 秒 |
| P95 响应时间 | 20.56 秒 |
| API 返回 token | 输入 21,048；输出 5,237；总计 26,285 |

门槛报告 SHA-256 为 `46f5afac0e7c4232dc037b583b6f3832a9b0d23f36860945cab6577ce188ce20`。API 未返回账单金额，且仓库没有固定的可核验单价，因此这里只记录服务端 token 用量，不把估算值表述为实际费用。

结论是 `glm-4.6v` 适合发现一部分问题和提供人工复核线索，但不具备自动放行资格。生产路径现在保持“确定性硬门可阻断、GLM 非通过结果进入人工复核、GLM 通过结果同样需要人工确认”；模型原始结果和问题仍保存在严格报告中。客户端已加入逐场景截图预览和人工确认，并把完成结果持久化为独立的 `hanengine.visual-review-proof/v1` sidecar；证明绑定报告 SHA-256、机器结论、全部场景图片哈希、确认时间和本地复核人，不修改机器报告。真实 v14 六场景已经完成 `1440x920` 首次生成和 `1120x720` 新窗口恢复检查。下一步应为 renderer 区域增加可验证的文本相交门；低对比度检测需先建立跨主题阴性样本，避免简单阈值造成误报。
