# HanEngine v1 发布范围

更新时间：2026-08-21

本文冻结 HanEngine v1 的产品边界、发布语义和退出条件。它优先于历史项目记录中的阶段性计划；各引擎的实际证据仍以 [引擎资源矩阵](engine-resource-matrix.md) 和 [真实授权项目验证记录](authorized-project-validation.md) 为准。

## 1. v1 的交付目标

v1 是一个本地优先的桌面工具，用于将用户合法拥有或获明确授权的**明文、结构化游戏文本**提取、翻译、校验并构建到源项目之外的独立候选目录。标准工作流必须提供：

- 引擎检测和能力说明；
- 原生本地化资源或结构化数据的文本写回；
- 占位符、编码、源树和候选产物哈希验证；
- 未处理项目、未译文本和失败原因的可见报告；
- 可恢复的任务、取消、重试和独立输出；
- Electron 桌面端的普通模式和专业模式。

v1 的核心体验是可审计的结构化文本汉化，不是对所有游戏资源进行自动视觉重绘。

普通模式不要求用户事先准备 JSON 术语表。用户可以先提取并查看文本；本地术语表属于专业模式的可选覆盖。没有配置翻译服务时，工具必须显示“待翻译/未完成”状态，不能把原文回写后宣称汉化成功。默认云端服务只有在 endpoint、隐私和令牌策略经过正式验证后才可提供。

## 2. 受支持的文本输入

| 引擎 | v1 明文输入 | 当前能力等级 | 发布说明 |
| --- | --- | --- | --- |
| Ren'Py | `game/**/*.rpy`，不含 `game/tl/` | `verified` | 对白、菜单和静态 screen 文本使用 Ren'Py 原生翻译输出；复杂动态表达式保留并报告。 |
| RPG Maker MV | `data/*.json` | `implemented` | 结构化文本、名称和事件写回已实现；Hello Underworld v15 是固定项目的 `build_ready` 非美术文字候选，不是通用认证。 |
| RPG Maker MZ | `data/*.json` | `implemented` | 已有结构化构建链路，尚无真实项目 `verified` 记录。 |
| Godot | 原始项目 PO | `verified` | 已有固定 Godot 4.7.1 PO 写回认证。 |
| Godot | 原始项目 CSV | `implemented` | 支持受限于目标列和可静态定位的文本；不外推为通用动态文本支持。 |
| Unity | 原始工程 XLIFF/CSV | `implemented` | 仅明文工程资源；尚无真实项目 `verified` 记录。 |
| Unreal Engine | 原始工程 PO | `implemented` | 仅明文工程资源；尚无真实项目 `verified` 记录。 |

`implemented` 表示代码和合成样例闭环可用，不等于对任意游戏或版本的发布承诺。桌面端和文档必须显示该差异；没有真实项目证据的适配器不得对外标为 `verified`。

## 3. v1 明确排除的范围

- 加密、DRM、封装二进制、反编译、进程注入、内存读写和协议拦截；
- 复杂运行时拼接、脚本求值和无法安全静态定位的动态文本；
- 不支持的引擎版本、插件格式和已打包游戏的自动修改；
- 自动 OCR 翻译、字体识别、纹理修补、原作风格重绘和视频逐帧字幕重制；
- 将单个项目截图、人工试玩或模型判断外推为某一引擎的通用认证。

## 4. 美术资源的处理边界

图片和视频文字遵循 [美术资源汉化流程](raster-resource-localization-workflow.md)。清单、人工审批、源/产物哈希和独立候选合并保留为独立实验能力，但**不属于 v1 默认流程，也不作为 v1 发布验收项**。

使用 `--raster-manifest` 时，只有逐资源人工批准且哈希完整匹配的产物才可进入候选；未审批资源保持源版本。Hello Underworld 先前的局部视频替换在用户验收中出现明显卡顿，因此 v1 禁止把该方案作为默认写回或运行认证依据。后续只有在建立性能基线，并证明候选播放不劣于源项目后，才可单独恢复该路线。

## 5. 结论语义

| 结论 | 含义 |
| --- | --- |
| `failed` | 内部验证或已配置的外部验证失败，不能交付。 |
| `build_ready` | 结构化提取、翻译、构建和内部验证通过，但缺少至少一项要求的真实项目外部证据。 |
| `verified` | 固定的真实授权项目、资源范围和引擎版本同时通过内部验证、官方工具、字体覆盖和运行冒烟，且候选未被验证器改写。 |

`verified` 只认证记录中明确的引擎版本、项目和资源类型。它不表示译文经过语言出版审校，也不自动覆盖其他资源类型。

## 6. v1 发布验收

发布前必须满足以下条件：

1. 普通模式可以从受支持的明文项目完成检测、提取、翻译、校验、独立构建和结果查看；失败、取消和重试均能显示明确原因。
2. 构建不能修改源项目；源树、候选树、生成文件和支持资源均有可复核哈希；占位符、编码和未处理清单进入质量报告。
3. 对外宣称的 `verified` 引擎能力具有对应的脱敏真实项目证据。仍处于 `implemented` 的适配器必须在界面、CLI 和文档中保持该状态。
4. 发布级回归通过：Python 单元/契约/流程测试、Electron 测试、TypeScript 检查和 Vite 构建；并补充普通模式端到端、长文本溢出和漏译质量门。
5. Windows 安装包完成干净机器安装、升级、回滚和依赖锁定验证；不把开发环境或用户本地路径作为前提。
6. 密钥不写入仓库、日志、任务状态或桌面渲染进程；此前暴露过的密钥在发布前轮换。

## 7. 发布退出条件

v1 在第 6 节全部满足后才退出发布阶段。未完成真实项目认证的适配器可以作为明确标注为 `implemented` 的受限能力保留；若产品要求把它们作为正式已验证卖点，则必须先补齐相应项目、版本、官方工具和运行证据。

美术资源性能优化是独立后续里程碑，不阻塞 v1 结构化文本交付，也不得因赶发布降低默认播放性能或证据标准。
